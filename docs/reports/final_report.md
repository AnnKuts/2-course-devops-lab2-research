## Тестове середовище

Всі експерименти було запущено локально на Mac (архітектура ARM64, що видно по завантаженню `aarch64` пакетів у логах). 

Для забезпечення відтворюваності, було написано bash-скрипт `run_experiments.sh`, який послідовно збирає всі образи і виводить час та розмір. Щоб повторити заміри, достатньо просто запустити:
```bash
./run_experiments.sh
```
Або можна зібрати конкретний образ вручну, наприклад:
```bash
docker build -t py-optimized -f python-app/Dockerfile.good ./python-app
```

Усі сирі логи виконання скрипта з виводом часу та розмірів можна подивитись у файлі [my_results_full.log](../../my_results_full.log).

### Python застосунок
- Було розділено копіювання залежностей та копіювання коду. Якщо спочатку зробити `COPY requirements/` і `RUN pip install`, а вже потім `COPY . /app`, то при зміні коду залежності не перевстановлюються. На практиці час перезбірки при зміні коду впав з 19 секунд до 1.79 с. Більш детально описано в [python_experiments.md](./python_experiments.md).
- Перехід на `alpine` очікувано зменшив розмір образу з 1.56GB до 162MB. Цікаво, що коли було додано `numpy`, виявилося, що для Alpine pip знайшов готові `musllinux` wheels. Тому час збірки був майже такий самий, як на Debian (близько 23 секунд), хоча зазвичай встановлення C-extensions на Alpine може займати багато часу через компіляцію. Розмір з `numpy` на Alpine вийшов 292MB, що все ще набагато менше за Debian (1.68GB).

### Golang застосунок 
- Звичайний образ на базі `golang:1.22` важить 1.33GB, бо містить весь компілятор та інструменти.
- Було спробувано використати multi-stage build — зібрати бінарник і покласти його в порожній образ `scratch`. Розмір став всього 16MB. Але довелося додати `CGO_ENABLED=0`, бо інакше бінарник шукав `libc` і падав з помилкою "no such file or directory". Мінус цього підходу — у `scratch` взагалі немає shell-у, тому зайти всередину контейнера для дебагу неможливо.
- Образ `distroless` від Google важить 59.5MB. Там є мінімально необхідні системні речі (наприклад, `glibc` і сертифікати), що дозволяє динамічну лінковку. Це зручніше, але shell там теж вирізаний задля безпеки. Більш детально в [golang_experiments.md](./golang_experiments.md).

### DNS Резолвінг
Було запущено локальний DNS-сервер (через dnsmasq) і два контейнери — ubuntu та alpine, щоб перевірити їхню поведінку:
- Glibc (Ubuntu) нормально підтягує пошукові домени. При запиті до `myservice.internal`, він автоматично додав `.corp` і знайшов IP адресу.
- Musl (Alpine) сприйняв домен з крапкою як повне ім'я (FQDN) і відразу повернув NXDOMAIN, проігнорувавши search domain. 
Це пояснює, чому іноді виникають неочевидні баги в Kubernetes при використанні Alpine. Більше деталей та логи тестів є у файлі [dns_experiments.md](./dns_experiments.md).

## Висновки

- Інсталяція залежностей (`requirements.txt`, `package.json`, тощо) має виноситися в окремий шар до копіювання вихідного коду проєкту для економії часу при локальній розробці завдяки кешуванню шарів.
- Multi-stage збірки мають використовуватися для компільованих мов (Go, C++) з метою уникнення перенесення гігабайтів компіляторів у фінальний образ.
- Alpine Linux підходить для зменшення розміру образів, проте необхідно перевіряти сумісність. Хоча в тесті для numpy знайшлися готові musllinux wheels, іноді пакети можуть компілюватися з нуля. Крім того, варто пам'ятати про специфіку роботи DNS в musl.
